# motto-gemini-vision

On-demand vision for Motto's text-first main model: read **one local image**,
make **one stateless Gemini multimodal request**, return a **compact text
answer**. No second agent, no session, no transcript inheritance.

## What this is (and is not)

`motto_vision` is a **perception tool implemented by Gemini**, not a subagent:

```
Pi/Motto text main model
  → ordinary tool call
  → read one local image
  → one stateless Gemini multimodal request
  → compact text result
  → ordinary tool result
  → the main model keeps working
```

- No independent agent loop, no session, no transcript inheritance, no tools.
- The main model's transcript, repo content, AGENTS.md and system prompt are
  **never** attached to the Gemini request. Gemini only sees a fixed system
  instruction, the current `question`, and the current image.
- The image is sent to Google; the tool result is text only.

The runtime boundary is provider-neutral even though this pack currently ships
one Gemini adapter. A normalized `ObservationRequest` enters an injected
provider and a validated `ObservationResult` leaves it. The result always has
`answer`, `evidence`, `limitations`, `artifacts`, `provenance`, and
`status: complete | partial`; bbox, page, and timestamp locators are range
checked. The main model receives only the deterministic local text projection
(Conclusion / Evidence / Limitations when those sections are present). The
canonical result and traceable provenance are retained in tool `details`.
Provider wire JSON, image base64, API keys, and endpoint configuration never
enter tool content or the tool schema. Unknown canonical fields fail closed;
no second model call is used to repair formatting.

- The endpoint is a **fixed constant** — `https://generativelanguage.googleapis.com/v1/interactions`.
  It is not configurable and cannot be redirected by any environment variable,
  tool parameter, or user setting (a test locks this down), so the API key can
  only ever travel to Google.
- No `executionMode` override: the tool follows pi's default batch policy
  (stateless one-shot call, no shared resources).

## Install / load

Follow the repo pack flow (already deployed at `~/.pi/agent/extensions/motto-gemini-vision/`):

```bash
./scripts/maint/deploy.sh motto-gemini-vision
#    Subdirectory index.ts auto-discovery picks it up on next pi start (or /reload).
```

## Configuration (unified credential store)

The pack never owns or writes a secret file. The Google credential follows
this single-source chain:

```text
~/.config/motto/credentials/google      ← unique source, mode 0600
  → ~/.local/bin/motto-credential google  ← unique resolver
  → ~/.local/bin/motto-google-key         ← provider wrapper
  → pi models.json: google.apiKey = "!motto-google-key"   (wrapper on PATH)
  → ctx.modelRegistry.getApiKeyForProvider("google")   (extension reads here)
```

- To set it up: `mkdir -p ~/.config/motto/credentials && printf '%s\n' '<key>' >
  ~/.config/motto/credentials/google && chmod 600 ~/.config/motto/credentials/google`,
  then ensure `~/.pi/agent/models.json` registers a `google` provider with
  `apiKey: "!motto-google-key"` (the wrapper must be on PATH).
- The key no longer lives in `~/.pi/agent/auth.json` (verified: pi resolves the
  `!` reference for `getApiKeyForProvider` when no stored credential exists).
- The wrapper path is **machine-local config**, not repository content: the
  absolute path under `~/.local/bin` is generated by the bootstrap/setup flow
  when migrating to a new machine.

The `GEMINI_API_KEY` variable below is retained for standalone development and
the explicit live smoke test only, not as a repository configuration mechanism.

| Var | Default | Meaning |
|---|---|---|
| `GEMINI_API_KEY` | — | Standalone/live-smoke fallback only. In a running pi extension, the key is resolved via `ctx.modelRegistry` → models.json `!motto-google-key` → the unified store. |
| `MOTTO_VISION_MODEL` | `gemini-3.6-flash` | Model used for the interactions request. |
| `MOTTO_VISION_TIMEOUT_MS` | `30000` | Request timeout in ms. Must be a positive integer in `1000..120000`; malformed or out-of-range values fail with a clear config error. |

## Supported inputs

- One local **PNG / JPEG / WEBP** file; MIME is detected from **content
  magic bytes**, not the file extension.
- Relative paths resolve from the current working directory; absolute and
  `~/...` paths are accepted.
- Raw image size cap: **10 MiB** (a conservative ceiling that leaves headroom
  for the base64 + JSON overhead of an inline request). Oversized images must
  be compressed or downscaled first.
- Not supported: URLs, `attachment://N`, multiple images, PDF/video/audio,
  image generation/editing, resize/re-encode, OCR-specific engines, offline.

## Tool schema

```ts
motto_vision({ path, question })
```

- `path`: local PNG/JPEG/WEBP path (relative, absolute, or `~/`).
- `question`: a specific visual question — state the evidence to inspect,
  relevant constraints, and the desired output format.

### Examples

OCR:

```text
motto_vision({
  path: "scans/contract-page2.png",
  question:
    "Transcribe all visible text on this page exactly, preserving casing and punctuation. Mark any unreadable segment as [unreadable]."
})
```

UI screenshot debugging:

```text
motto_vision({
  path: "artifacts/settings.png",
  question:
    "Identify why the Save button appears disabled. Return: observed evidence, probable cause, and confidence. Do not infer invisible application state."
})
```

Diagram / architecture question:

```text
motto_vision({
  path: "docs/architecture.svg-render.png",
  question:
    "Which component sits between the API gateway and the database in this diagram? Quote any labels you can read and describe their spatial relationship."
})
```

> Ask a narrow, task-specific question rather than a generic full-image
> description — the tool is a visual evidence extractor, not a summarizer.

## Privacy

**The image bytes are sent to Google** (the Gemini Developer API Interactions
endpoint, `https://generativelanguage.googleapis.com/v1/interactions`). Only
use `motto_vision` when the image does not contain data you must not disclose.
The API key travels only in the `x-goog-api-key` header — never in the URL,
the tool result, logs, or error messages. Requests set `store: false` as an
explicit no-session instruction, but that flag is not an absolute zero-retention
or zero-processing guarantee; Google's current service terms, safety handling,
and account/project data controls still govern provider-side handling.

## Quotas

- No guarantees on free-tier or project quotas; current project limits and
  billing terms at [AI Studio](https://aistudio.google.com/) apply. A paid
  project does not turn this helper into an unlimited service, and a free tier
  may be unavailable or rate limited; inspect the provider's current terms for
  the account/project in use.
- This tool uses the **Gemini Developer API** only. It does **not** use Google
  AI Pro / Antigravity quota, OAuth, or any non-public endpoint.

## When to switch to a native multimodal main model

`motto_vision` is a by-request helper for a text-first model. Switch the main
model to a native multimodal one when:

- the task needs many consecutive images,
- vision is the primary object of work,
- you need fine-grained cross-image spatial reasoning,
- a task would require calling this tool repeatedly.

## Troubleshooting

Errors are fail-closed and typed for callers as `config`, `input`, `provider`,
`quota`, `timeout`, `aborted`, or `invalid_output`. HTTP 429 maps to `quota`,
5xx maps to `provider`, and the tool never retries or silently switches
providers.

| Symptom | Cause / fix |
|---|---|
| `Google Gemini API key is not configured` | Ensure `~/.config/motto/credentials/google` exists (0600) and `~/.pi/agent/models.json` registers the `google` provider with `apiKey: "!motto-google-key"` (wrapper on PATH), then restart pi. For standalone smoke set `GEMINI_API_KEY`; the tool never makes a network request without a key. |
| `HTTP 429` / `RESOURCE_EXHAUSTED` | Project quota exhausted. Check AI Studio project limits; no automatic retry is performed. |
| `HTTP 404` / model unavailable | `MOTTO_VISION_MODEL` is wrong or not enabled for the project; check the model name and quota. |
| `request timed out after Ns` | The request exceeded `MOTTO_VISION_TIMEOUT_MS`; raise it (max 120000) or reduce image size. |
| `image too large` | File exceeds 10 MiB; compress or downscale before calling. |
| `unsupported image format` | Only PNG/JPEG/WEBP by content magic bytes; SVG/GIF/AVIF/HEIC/TIFF are not converted or accepted. |
| `image not found` / `not a regular file` | Path resolution issue; paths resolve against the current working directory. |

## Current limitations

- Local single image only.
- No chat-attachment interception (`attachment://N`).
- No multi-image comparison.
- No resize/re-encode.
- No offline capability.
- No OCR-dedicated engine; OCR works through the general vision model.
- If an observation cannot be expressed reliably as compact, reviewable text
  (for example repeated image/video reasoning or cross-image work), do not
  chain this helper: switch to a native multimodal main model for a one-shot
  task instead.

## Development

```bash
npm test          # offline unit + integration tests (network fully mocked; no key needed)
npm run typecheck # tsc --noEmit
node --experimental-strip-types test/live.mts   # live smoke — SKIPs without a local credential
```

The live smoke test generates a small solid-red PNG, calls the real Gemini
API, verifies a non-empty answer identifying the color, and records model /
status / duration / usage. It resolves the key from pi's local credential
store (`~/.pi/agent/auth.json`, provider `google`), with a `GEMINI_API_KEY`
env fallback for portable/CI setups; without either it prints `SKIP` and
exits 0, so default regression never depends on it.

> Proxy note: on machines that route HTTPS through a local proxy (this one
> uses `127.0.0.1:9090`), the **standalone** live smoke needs
> `NODE_USE_ENV_PROXY=1` (Node ≥24 honors `HTTP(S)_PROXY` env then). Inside a
> running pi process the extension's `fetch` already uses pi's proxy-aware
> global dispatcher, so no extra setting is needed there.
